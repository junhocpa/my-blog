# 현재 상태 — 2026-08-08 시점에서 중단

## 한 줄 요약

**웹앱과 수집기는 완성됐지만, 네이버 모바일 API가 응답하지 않아 실제 수집은 되지 않는다.**
공개 사이트에는 예시 데이터로 화면만 동작한다. 사용자 요청으로 여기서 작업을 멈췄다.

## 막힌 것

**`m.land.naver.com` 의 매물 API가 HTTP 200 과 함께 본문 `null`(4바이트)만 돌려준다.**
차단(403/429)이 아니라 200 + 빈 내용이다.

### 시험한 것과 결과 (전부 실패, 모두 동일하게 `null`)

| # | 시험 내용 | 결과 |
|---|---|---|
| 1 | `articleList` + `view=atcl` + `sameAddressGroup` + `wprcMin/Max` (최초 형태) | 200 / `null` |
| 2 | 위 + `itemId`·`mapKey`·`lgeo`·`showR0` 빈 값 추가 | 200 / `null` |
| 3 | `X-Requested-With: XMLHttpRequest` + 지도형 `Referer` 추가 | 200 / `null` |
| 4 | 형태 A — 실제 구현체 기준 최소형 (`view`/`sameAddressGroup`/금액필터 제거, `sort=rank`) | 200 / `null` |
| 5 | 형태 B — A + `wprcMin/wprcMax` | 200 / `null` |
| 6 | 형태 C — 옛 형태 재현 (비교용) | 200 / `null` |
| 7 | `clusterList` (`pCortarNo={줌}_{법정동코드}`, `addon=COMPLEX` 등 교정형) | 200 / `null` |
| 8 | 쿠키(세션) 첨부 | 무의미 — 아래 참조 |
| 9 | **브라우저 주소창에서 직접 열기** (쿠키·정상 헤더 자동 포함) | 200 / `null` |

### 이로부터 확정된 것

- **차단이 아니다.** 200 응답이고 robots.txt 도 제한이 없다.
- **URL 파라미터 조합 문제가 아니다.** 6가지 형태가 모두 동일하게 `null` 이다.
- **쿠키·세션 문제가 아니다.** 브라우저에서 열어도 `null` 이므로 쿠키 가설은 기각됐다.
- `regions/list` (PC 호스트 `new.land.naver.com`) 는 **첫 요청부터 HTTP 429** 를 준다.
  요청 2건뿐이었으므로 실제 요청 과다가 아니라 거절로 보인다. 그래서 여의도동 `cortarNo`
  (`1156011000`) 를 `config.json` 의 `regions.manual` 에 직접 넣어 우회해 둔 상태다.

### 아직 확인되지 않은 것 (다시 시작할 때 첫 번째로 할 일)

**실제 네이버 페이지가 보내는 요청을 확인하지 못했다.** 이것이 유일하게 남은 미확인 지점이다.

브라우저 주소창 테스트는 완전히 결정적이지 않다. 주소창으로 열면 브라우저가 페이지 이동
요청으로 보내지만(`Sec-Fetch-Mode: navigate`, `Accept: text/html`), 페이지 안에서
자바스크립트가 보내는 요청은 종류가 다르다(`Sec-Fetch-Mode: cors`, `Sec-Fetch-Site: same-origin`).
네이버가 이 차이로 걸러낼 수 있으므로, **실제 XHR 요청은 아직 살아있을 가능성이 있다.**

확인 방법:

1. 크롬에서 `m.land.naver.com` 접속
2. 여의도동 → 아파트 → 전세로 검색해 매물 목록이 보이게 한다
3. F12 → Network 탭 → 상단 필터에 `article` (없으면 `ajax` 또는 `cluster`)
4. 매물 목록을 아래로 한 번 스크롤
5. 뜨는 요청을 클릭 → Headers 탭 → `Request URL` 과 `Request Headers` 확인
6. 그 요청을 우클릭 → Copy → Copy as cURL (bash)

여기서 얻은 실제 URL·헤더와 `collector/naver-client.js` 의 `buildArticleListUrl` 을
대조하면 차이를 바로 맞출 수 있다.

## 다시 시작할 때의 선택지

1. **실제 요청 확인 후 URL 교정** — 위 절차로 얻은 요청과 대조. 성공하면 나머지는 그대로 동작한다.
   가장 적은 작업으로 끝나는 길이다.
2. **브라우저 자동화(Playwright)로 전환** — 진짜 브라우저를 띄워 화면을 조작한다. 막힐 가능성이
   낮지만 `CLAUDE.md` 의 "외부 라이브러리 최소화" 원칙과 충돌하고 설치가 무겁다(수백 MB).
   **별도 승인이 필요하다** (spec 11장 D6에서 승인 없이 도입하지 않기로 정했다).
3. **자동 수집을 포기하고 직접 입력형으로 전환** — 웹앱 화면·필터·평단가 분석·배지는 그대로 쓰고,
   매물만 손으로 입력·관리한다.

## 남은 알려진 문제 (수집이 되기 시작하면 확인할 것)

- 승인된 대상 지역은 7곳(여의도·당산·문래·영등포·양평·신길·노량진)인데, `regions/list` 가 429로
  막혀 `regions.manual` 로 **여의도동 하나만** 설정돼 있다. 나머지 6곳의 `cortarNo` 확보 방법이 필요하다.
- `V6`(429 발생 임계) 는 의도적으로 시험하지 않는다. 임계를 찾으려면 일부러 차단을 유발해야 한다.
- `build.js` 가 `apps/` 를 통째로 복사하므로 로컬 실데이터·`run-logs` 도 `dist/` 로 복사된다.
  단 해당 파일들은 gitignore 되어 GitHub Actions 클린 빌드에는 존재하지 않으므로 공개 사이트는 안전하다.
  `dist/` 를 손으로 배포하지만 않으면 된다.
- 리뷰에서 발견해 남겨둔 항목은 `review.md` 4장 참조.
