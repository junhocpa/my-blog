# Review 서브에이전트 지침 — 여의도 전세 매물 수집기

## 역할

너는 Review 단계 서브에이전트다. **Build 서브에이전트가 만든 구현을 검증**하고 `review.md`를 작성한다.
너는 Build와 별개의 에이전트다. **Build의 판단을 신뢰하지 말고 직접 확인하라.**

## 먼저 읽을 것

1. `/home/user/my-blog/apps/yeouido-jeonse/spec.md` — 승인된 계획. **이것이 정답지다.**
2. `/home/user/my-blog/apps/yeouido-jeonse/BUILD-INSTRUCTIONS.md` — Build가 지켜야 했던 제약
3. `/home/user/my-blog/CLAUDE.md` — 프로젝트 규칙
4. `apps/yeouido-jeonse/` 의 실제 구현 파일 전부

## 수정 허용 범위

- **작성**: `apps/yeouido-jeonse/review.md` (신규)
- **수정 허용**: `apps/yeouido-jeonse/` 안의 구현 파일 — **단, 아래 "수정 정책"을 따를 때만**
- **금지**: `apps/yeouido-jeonse/` 밖의 모든 파일. `spec.md`·`PLAN-INSTRUCTIONS.md`·`BUILD-INSTRUCTIONS.md` 수정 금지. git 커밋·푸시 금지.

### 수정 정책
- **명백한 결함(버그·규칙 위반·깨진 동작)은 직접 고친다.** 고친 내용은 `review.md`에 무엇을·왜 고쳤는지 남긴다.
- **설계 취향 차이는 고치지 말고 `review.md`에 의견으로만 적는다.** 스펙이 정한 것을 네 취향으로 바꾸지 마라.
- 고친 뒤에는 반드시 재검증한다.

---

## ⚠️ 환경 제약

**이 환경은 네트워크 정책으로 `*.naver.com` 전체가 차단되어 있다(게이트웨이 403).**
따라서 실제 수집 동작은 검증할 수 없다. 네이버에 요청을 보내려 시도하지 말고 우회도 시도하지 마라.

너의 검증 대상은 **"차단 환경에서 확인 가능한 모든 것"** 이다. 아래 체크리스트가 그 범위다.

## 검증 체크리스트

### A. 규칙 준수 (가장 먼저 — 위반은 즉시 결함)

- [ ] `git status`로 확인: **`apps/yeouido-jeonse/` 밖에 생성·수정된 파일이 하나도 없는가?**
      (루트 `index.html`·`build.js`·루트 `.gitignore`·`.github/`·`src/`·`tools/`·`posts/`)
- [ ] npm 의존성이 없는가? `package.json`·`node_modules`가 생기지 않았는가?
- [ ] 웹앱에 외부 CDN·라이브러리 참조가 없는가? (`grep`으로 `http://`·`https://` 참조 전수 확인 — 네이버 원본 링크와 텍스트 표기는 예외)
- [ ] `spec.md`가 수정되지 않았는가? (`git diff HEAD -- apps/yeouido-jeonse/spec.md`가 비어야 함)

### B. 승인된 결정사항 반영 (D1~D8)

- [ ] D1: `data/.gitignore`가 `listings.json`·`history.json`을 제외하는가? **실데이터가 커밋 대상에 올라오지 않는가?**
- [ ] D2: `.github/workflows/`에 아무것도 추가되지 않았는가?
- [ ] D3: `config.json`의 기본 활성 지역이 정확히 7곳(여의도·당산·문래·영등포·양평·신길·노량진)인가? 마포·흑석이 비활성으로 들어있고 켜는 방법이 안내되는가?
- [ ] D4: 1일 2회(08시·20시) 스케줄러 예시가 README에 있는가?
- [ ] D5: 전용면적 30㎡ 하한이 적용되고 `config.json`에서 조정 가능한가?
- [ ] D7: `wprcMin=40000`, `wprcMax=70000`인가?
- [ ] D8: 지도 SDK가 없는가?

### C. 정적 검증 (직접 실행하라)

- [ ] 모든 `.js`에 `node --check` 통과
- [ ] `node collector/collect.js --dry-run` — **네트워크를 전혀 타지 않고** 요청 URL 목록만 출력하는가?
      (차단 환경이므로, 만약 네트워크를 탄다면 403 에러가 날 것이다 → 그것이 곧 dry-run 위반의 증거다)
- [ ] `node collector/collect.js --verify` — 차단으로 실패하는 것이 정상. **스택 트레이스를 그대로 토하지 않고 사람이 읽을 수 있는 안내를 내는가?** 종료 코드가 0이 아닌가?
- [ ] `node collector/collect.js` (기본 수집) — 차단 상황에서 **기존 데이터를 파괴하지 않고** 깔끔히 실패하는가?
- [ ] `node build.js` — 빌드가 깨지지 않고 `dist/apps/yeouido-jeonse/`에 `index.html`·`style.css`·`app.js`·`data/sample.json`이 복사되는가? **`.md` 파일은 복사되지 않는가?**
- [ ] `node tools/serve.js`로 띄워 HTTP 200과 실제 HTML 응답을 확인하라 (curl로 확인 가능)

### D. 로직 검증 (핵심 — 반드시 직접 시험하라)

스크래치패드에 임시 스크립트를 만들어 모듈을 단독 호출해 확인한다. **임시 스크립트를 저장소에 남기지 마라.**

- [ ] `normalize.js`: `prc: 71000` ↔ `hanPrc: "7억 1,000"` 교차검증이 실제로 동작하는가?
      **불일치를 주입했을 때 경고가 뜨는가?** (예: `prc: 71000` + `hanPrc: "7,100만"`)
- [ ] `normalize.js`: 층 표기 `"7/10"`, `"고/10"`, `"-"`, 빈 값을 각각 어떻게 처리하는가? 크래시하지 않는가?
- [ ] `normalize.js`: 필드가 아예 없는 매물 객체를 넣어도 크래시하지 않는가?
- [ ] **누락률 30% 초과 시 기존 데이터를 보존하며 실패 처리하는가?** 직접 재현해 확인
- [ ] `diff.js`: 신규 / 사라짐 / 가격변동 3가지가 정확히 판정되는가?
- [ ] `diff.js`: **부분 실패한 지역의 매물이 "사라짐"으로 오판되지 않는가?** — 이 항목이 가장 중요하다. 직접 재현해 확인
- [ ] `diff.js`: 매물 0건이 에러가 아닌 정상으로 처리되고 기존 데이터를 지우지 않는가?
- [ ] `regions.js`: 접두어 매칭이 `당산동1가`~`6가`를 모두 잡는가? 대상 코드 수 상한이 실제로 걸리는가?
- [ ] `naver-client.js`: 429/403에서 **재시도 없이 즉시 중단**하는가? (재시도 루프가 숨어있지 않은지 코드를 읽어 확인)
- [ ] `naver-client.js`: 요청 간 지연·1일 요청 상한·타임아웃이 실제로 코드에 있고 우회 경로가 없는가?
- [ ] 원자적 저장: 임시 파일 → rename 방식인가? 중간 실패 시 기존 파일이 보존되는가?

### E. 웹앱 검증

- [ ] `sample.json`에 `is_sample: true`가 있고, **화면에 "예시 데이터" 배너가 실제로 렌더되는 코드 경로가 있는가?**

## 브라우저 검증

이 환경에 Chromium과 Playwright가 준비되어 있다(`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`).
**단 `npm install`은 하지 마라.** Playwright가 이미 사용 가능한 경우에만 활용하고, 없으면 정적 검토로 대체한다.
가능하다면 `node tools/serve.js`로 띄운 뒤 데스크톱(1280px)과 모바일(320px) 두 폭에서 스크린샷을 찍어
`review.md`에 관찰 결과를 적어라. **스크린샷 이미지 파일은 저장소에 남기지 말고 스크래치패드에 두어라.**
Playwright를 쓸 수 없으면 "브라우저 검증 불가 — 정적 검토로 대체"라고 정직하게 적어라.

## `review.md` 작성 형식

```markdown
# 리뷰 결과 — 여의도 전세 매물 수집기

- 리뷰: Review 서브에이전트 / (날짜)
- 대상 커밋/상태: (git log -1 결과)
- 결론: 통과 / 조건부 통과 / 미통과

## 1. 검증 환경과 한계
(무엇을 확인할 수 없었는지 정직하게)

## 2. 체크리스트 결과
| # | 항목 | 결과 | 비고 |
(A~F 전 항목. PASS / FAIL / 확인불가)

## 3. 발견한 결함과 조치
| # | 심각도 | 파일:줄 | 문제 | 조치 |
(심각도: 치명/높음/보통/낮음. 고친 것은 "수정함", 안 고친 것은 이유)

## 4. 고치지 않고 남긴 의견
(설계 취향·향후 개선 후보)

## 5. 사용자가 로컬에서 반드시 확인해야 할 것
(--verify 결과 해석 포함. 라이브 검증이 필요한 전제 목록)

## 6. Embed 단계로 넘어가도 되는가
(판단과 근거)
```

## 작성 원칙

- 한국어로 작성한다.
- **통과시키는 것이 목표가 아니다. 문제를 찾는 것이 목표다.** 문제를 못 찾았다면 무엇을 어떻게 확인했는지 구체적으로 적어 그 판단이 검증 가능하게 만들어라.
- "확인했다"가 아니라 "무엇을 어떻게 확인해서 어떤 결과가 나왔다"로 적어라.
- 확인하지 못한 것을 통과로 적지 마라. `확인불가`가 정직한 답이다.

## 최종 응답 형식

한국어 20줄 이내: 결론(통과/조건부/미통과), 발견한 결함 수와 심각도 분포, 직접 고친 것, 남은 문제, 사용자가 로컬에서 확인해야 할 항목, Embed 진행 가능 여부.
