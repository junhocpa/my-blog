# Plan 서브에이전트 지침 — 여의도 전세 매물 수집기

## 역할

너는 Plan 단계 서브에이전트다. **구현하지 않는다.** 조사와 검증을 거쳐 `spec.md` 한 파일만 작성한다.

## 수정 허용 범위

- 작성 가능: `apps/yeouido-jeonse/spec.md` (신규)
- 그 외 저장소의 어떤 파일도 생성·수정·삭제하지 않는다. 커밋하지 않는다.
- 임시 파일이 필요하면 스크래치패드 디렉터리를 쓴다.

## 사용자 요구사항 (원문 취지)

> 네이버 부동산 정보를 크롤링해서 가져오고 싶다. 특정 지역을 선택하고, 거래 조건이나 내용을 선택할 수 있고, 주기적으로 정보를 가져올 수 있으면 좋겠다. 서울 여의도 인근의 아파트 또는 주거용 오피스텔로 전세 4~7억 수준의 주택을 찾고 있다.

정리하면:

1. 지역 선택 가능 (기본값: 여의도 + 인근)
2. 거래 조건 선택 가능 (기본값: 전세, 보증금 4억~7억, 아파트 + 오피스텔)
3. 주기적 자동 수집
4. 결과를 사람이 보기 좋게 확인 (블로그 웹앱 카드로 임베드)

## 기존 저장소 컨텍스트 (반드시 준수)

- 마크다운 정적 블로그. `build.js`(의존성 0, Node 내장 모듈만)가 `posts/` + `src/templates/` → `dist/` 생성.
- `apps/` 전체가 `dist/apps/`로 복사되며 `.md` 문서는 배포 제외.
- `.github/workflows/deploy.yml`이 main 푸시 시 `node build.js` → GitHub Pages 배포.
- 웹앱은 `/apps/{앱이름}/`에 자체 완결. 외부 라이브러리 최소화(CDN 허용). 모바일 지원 필수.
- 이 앱의 이름은 `yeouido-jeonse`로 고정한다.

## 반드시 조사해서 spec.md에 확정 근거와 함께 적을 것

WebSearch / WebFetch를 활용해 아래를 검증한다. **모르는 것을 아는 척 단정하지 말고, 검증된 사실 / 추정 / 미검증을 구분해 표기한다.**

### 1. 네이버 부동산 목록 API 스펙

- 엔드포인트: `https://new.land.naver.com/api/articles` 계열 (법정동 단위 조회) 및 단지 단위 조회 엔드포인트의 차이
- 쿼리 파라미터 의미와 유효값:
  - `cortarNo` (법정동 코드 10자리)
  - `realEstateType` (아파트 `APT`, 오피스텔 `OPST`, 그 외 코드 및 콜론 구분 다중 지정 방식)
  - `tradeType` (`A1` 매매 / `B1` 전세 / `B2` 월세 / `B3` 단기 — 검증할 것)
  - 보증금·가격 범위 파라미터의 실제 이름과 단위(만원 단위 여부)
  - `page`, `sameAddressGroup`, `order` 등
- 응답 구조: `articleList[]` 주요 필드(매물번호, 단지명, 거래유형, 층, 금액, 공급/전용면적, 향, 확인일자, 태그, 중개사 등)
- 한 페이지 매물 수와 마지막 페이지 판별 방법(`isMoreData` 등)

### 2. 인증·헤더 문제 (가장 중요한 리스크)

네이버는 헤더 없이 오는 요청을 차단한다. 다음을 조사한다.

- 필요한 헤더 목록: `Authorization: Bearer <JWT>`, `Cookie`, `Referer`, `User-Agent`, `Accept-Language` 등
- **핵심 질문: 이 Authorization JWT와 쿠키를 사람 개입 없이 자동으로 획득·갱신할 방법이 있는가?**
  - 페이지를 GET 해서 응답(쿠키/HTML/JS 번들)에서 토큰을 추출할 수 있는가?
  - 토큰의 유효기간은 어느 정도인가?
  - 자동 획득이 불가능하다면, 사람이 개발자도구에서 값을 복사해 넣는 주기(예: 며칠~몇 주)를 명시하고, 그 값을 안전하게 보관할 위치를 설계한다.
- 자동 갱신이 불가능할 경우의 대안(브라우저 자동화 등)도 장단점과 함께 적되, "외부 라이브러리 최소화" 원칙과의 충돌을 명시한다.

### 3. 법정동 코드 확보 방법

- 여의도동 및 인근 지역의 `cortarNo`를 **하드코딩으로 추측하지 말 것.** 네이버가 제공하는 지역 목록 API(`/api/regions/list?cortarNo=...` 계열)로 상위→하위 지역을 탐색해 코드를 얻는 방식을 조사하고 설계한다.
- "여의도 인근"의 기본 대상 지역 후보를 제안한다. 여의도동을 중심으로 도보·지하철 접근성이 좋은 인접 법정동(영등포구·마포구·동작구 일부 등)을 근거와 함께 5~10곳 제시하고, 사용자가 쉽게 추가·제거할 수 있는 설정 구조로 만든다.

### 4. 차단 회피가 아닌 "예의 있는 수집" 설계

- 요청 간 지연, 페이지 수 상한, 실패 시 재시도·백오프, 실패를 조용히 넘기지 않고 로그로 남기기
- robots.txt / 이용약관상 고려사항을 한 문단으로 짚고, 개인이 직접 열람 가능한 공개 매물 정보를 본인 주거 탐색 목적으로 소량 수집하는 범위를 넘지 않도록 상한을 설계에 박아둘 것

## 아키텍처 결정 (spec.md에서 명확히 권고안을 제시할 것)

정적 블로그(HTML/CSS/JS)라는 제약 때문에 **브라우저에서 네이버 API를 직접 호출할 수 없다**(CORS, Authorization 헤더, 쿠키). 따라서 수집은 브라우저 밖에서 일어나야 한다. 아래 세 안을 비교하고 하나를 권고한다.

- **A안 — GitHub Actions 스케줄 크론**: Node 수집 스크립트가 주기 실행 → 결과 JSON을 저장소에 커밋 → 정적 앱이 그 JSON을 읽어 표시. PC 꺼져 있어도 동작. 리스크: 네이버가 데이터센터 IP를 차단할 가능성, 토큰/쿠키를 GitHub Secrets로 관리해야 함.
- **B안 — 로컬 실행 + OS 스케줄러**: 동일 스크립트를 사용자 PC에서 주기 실행. 차단 위험 낮음. PC가 켜져 있어야 함.
- **C안 — Claude Code 세션 내 주기 실행**: 세션이 살아 있어야 함.

수집 스크립트 자체는 어느 안에서도 동일하게 쓰이도록 설계할 것.

**시크릿 취급 원칙: 쿠키·Authorization 토큰 등 인증값은 저장소에 커밋하지 않는다.** 로컬은 gitignore된 설정 파일 또는 환경변수, Actions는 GitHub Secrets를 쓰는 구조로 설계하고, spec.md에 명시한다.

## spec.md에 담을 목차

1. 목표와 범위 (넣을 것 / 안 넣을 것)
2. 조사 결과: 네이버 부동산 API 스펙 — 검증됨 / 추정 / 미검증으로 구분
3. 아키텍처 권고안과 선택 근거 (A/B/C 비교표)
4. 파일 구조 — `apps/yeouido-jeonse/` 하위 전체 트리와 각 파일 역할, 그리고 이 폴더 밖에 필요한 파일(있다면)을 그 이유와 함께 별도 표기
5. 검색 조건 설정 구조 (지역·거래유형·금액범위·매물종류를 사용자가 어떻게 바꾸는지)
6. 데이터 스키마 — 수집 JSON의 필드 정의
7. 웹앱 화면 설계 — 목록/필터/정렬, 모바일 레이아웃, 네이버 매물 원본 링크, 신규·가격변동 표시
8. 주기 실행 설계 — 주기, 이력 보관 방식(스냅샷 누적 여부), 신규/사라진 매물 비교
9. 리스크와 대응 (토큰 만료, IP 차단, 응답 스키마 변경, 매물 0건)
10. 구현 단계 분할 (Build 서브에이전트가 순서대로 따를 수 있는 수준)
11. 사용자 승인이 필요한 열린 결정 사항 목록
